Staging Redesign

One design for the packet's flows, built from fresh research on what Fork and git actually do. The design rules come first. Then each flow is shown screen by screen, followed by its choices. Every choice starts on its recommendation, so you only touch what you want to change. When you're done, use Copy answers at the bottom and paste the result into the chat. No code changes until you've approved this.

Three earlier decisions rested on wrong Fork claims. I checked each one against Fork's own issue tracker.
  • Several selected files. Fork doesn't draw several selected files' diffs together; it shows the first file only (fork-dev/Tracker #261, TrackerWin #786).
  • Stage All. Fork's modifier key for Stage All is Shift, not Alt (TrackerWin #2429).
  • Merge comment lines. Committing git's # Conflicts: lines is a Fork bug that has been open since 2017 (Tracker #180), not a Fork design.
These came through me as "as Fork does". The flows below correct them.

Design rules

Every flow below follows these rules. Approve them, or mark any to discuss.

1. Fork first, checked at the source
Where Fork's behaviour is known, Cairn does the same. Every "as Fork does" cites the Fork issue or release note it comes from.
2. One confirmation rule
An operation you can't undo, or one that rewrites history someone else may have, always gets the same confirmation dialog: Cancel has focus, and Escape goes back one step. An operation you can recover from asks nothing. The button and the keyboard chord always do the same thing.
3. Ask the cost at the press
Cairn works out what an operation will destroy when you press its button, not on every refresh beforehand. No "reading…" button states.
4. One home for each kind of message
  • Progress shows in the title-bar status box.
  • A git failure opens Fork's Git Error dialog.
  • A refusal Cairn finds while running opens the same dialog, titled "Couldn't <name>".
  • A refusal Cairn knows in advance shows as a greyed control with its reason beside it.
  • Success says nothing.
  • A cancel opens no dialog.
There is no line under the file lists.
5. One name per operation
Fork's imperative name ("Stage 2 files", "Commit", "Create branch 'x'") everywhere it appears. Four status words: running, succeeded, failed, cancelled.
6. Short text, never cut
Never cut off text you need to read; make it short instead. Never repeat what's already on screen. Per-file detail goes behind "Show files".
7. Let git decide
Run git and show its refusal, rather than predicting what git would do. The message you see is the message that gets committed.
8. One selection, one scope
You select files in one list. The diff shows one file. Every route — chord, button, drag, menu — acts on what's selected, wherever focus is.

1. Local Changes: selecting and staging

Today "what is selected" is kept in three places that have to be kept in step by hand: the list's selection, the file whose diff is shown, and the set of files drawn together. 2. Committing and amending

Amend has one confirmation dialog, used only when the amend matters: the commit is already on a remote, or the old commit can't be recovered. Otherwise it is one press, with no line under the button, and the chord does exactly what the button does. A hook failure always goes to Fork's Git Error dialog. Its skip runs once, never asks a second time, and sits in the dialog's footer for commits and amends alike.

3. Discarding

Every destructive prompt uses one sentence frame: <Question naming what is discarded>? [The worst loss, only when it's worse than changes.] You can't undo this. Per-file detail goes behind "Show files". The dialog opens at once; while Cairn counts, it says "Counting…" and the button is greyed, so a large selection never leaves you waiting with nothing on screen.

4. Create Branch

The dialog stays open beneath any confirmation or error, so Cancel takes you back with everything as you left it.

Git reproduced in throwaway repositories shows two things:

  • A plain git checkout -b refuses where an untracked file is in the way, and then creates no branch.
  • Ignored files are lost on any checkout, so that loss isn't specific to Discard.

5. Progress, errors and the activity popover

Today a message can appear in eight places, and the popover has eight status words. The redesign gives each kind of message one home (rule 4) and uses Fork's Activity Manager for the popover.

Fork does offer to remove index.lock (release notes 2.39: "Propose to remove index.lock file if repository is locked"), but only as part of the failure. A leftover lock becomes one state of the repository, decided by whether the file exists now.
